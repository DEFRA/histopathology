## 1. System Overview

The Histopathology System is an internal web application that manages the end-to-end lifecycle of pathology submissions from receipt through processing, histology referencing, reporting, and archiving. It is used exclusively by Crown Commercial Property laboratory staff and their customers (external submitters).

The system runs as an **ASP.NET WebForms application** on **IIS**, targeting **.NET Framework 4.0**, with a **Microsoft SQL Server** back-end reached exclusively through stored procedures.

### Functional summary

| Function | Pages | Description |
|---|---|---|
| Submission management | `AddSubmission`, `SubmissionForm`, `SubmissionDetails`, `ViewSubmissions`, `EditBatch` | Create, view, edit, and copy pathology submissions (batches) |
| Sample / animal entry | `AddSample`, `ViewSamples`, `CopySamples` | Add animals/samples to a batch; copy between batches |
| Block management | `BlockDetails`, `BatchBlocks`, `CopyBlocks`, `BookBlockRef`, `BookHistologyRef` | Manage histology blocks; book and assign histology references |
| Batch lifecycle | `ReceiveBatch`, `BatchDetails`, `BatchSummary`, `FinalPrintBatch` | Receive, process, and print batches |
| Dispatch and archiving | `BatchesForDispatch`, `BatchesForArchiving`, `ArchiveBlocks`, `ArchiveTissues` | Dispatch and archive completed batches |
| Quality control | `QCNotes`, `QCNoteForm`, `EditQCNote`, `QualityData` | Record and review quality-control notes |
| Searching | `SearchSubmissions`, `SearchSample`, `SearchSender`, `SearchTest`, `SearchBlockRefs` | Cross-cutting search across submissions, samples, blocks |
| Audit logging | `AuditLogByDate`, `AuditLogByUser`, `AuditLogBySubmission` | View audit trails by date, user, or submission |
| Pick-list maintenance | `PickListMaintenance`, `PickListMaintenanceID`, `PickListUserArea` | Maintain reference/lookup tables |
| User maintenance | `UserMaintenance` | Manage application users and area assignments |
| Reporting | 9 Crystal Reports (`.rpt`) | PDF reports for submissions, histology, QC notes, blocks |
| Export | `ExcelExport` | Export search results to Excel |
| Help | `HistoHelp_CustomerGroup.htm`, `HistoHelp_HistoGroup.htm` | Static HTML help pages differentiated by user group |

## 3. Major Components

### 3.1 Web Layer (`HistopathologySystem`)

- **Entry point:** `Home.aspx` — the dashboard page after IIS Windows Authentication completes
- **Layout:** Every page includes `VLAHeader.ascx` (top navigation + identity context) and `VLAFooter.ascx` (footer). There is no Master Page; each ASPX declares the header/footer controls directly.
- **User controls:** 8 ASCX controls handle shared UI behaviour:
  - `VLAHeader.ascx` — displays user/group/batch context; resolves Windows NT identity on first load; owns breadcrumb navigation
  - `VLAFooter.ascx` — static footer
  - `Batch.ascx` — batch detail display component used across multiple pages
  - `CalendarDate.ascx` — date picker control
  - `HistologyRef.ascx` — histology reference picker
  - `MouseNumber.ascx` — mouse/sample number input with enter-key wiring
  - `SenderRef.ascx` — sender reference input with mandatory flag
  - `DataGridPager.ascx` — custom DataGrid pager

### 3.2 Domain Library (`HistopathologyLib`)

Stateless class library containing domain objects. Every class inherits from `TBCultureDA` (the logging DA wrapper) and calls stored procedures directly. No ORM. No interfaces. Classes are instantiated inline in ASPX code-behind.

### 3.3 Data Access Layer (`DataAccessLib`)

Two-tier ADO.NET wrapper:
- `DataAccess` (in `clsDataAccess.vb`) — low-level Shared methods: `ExecuteNonQuery`, `ExecuteQuery`, `FillDataSet`, `FillDataTable`, `UpdateDataSet`. Reads connection string from `AppSettings("DBConnectionString")` via a lazy-initialised Shared field.
- `TBCultureDA` — thin wrapper over `DataAccess`; all calls pass through here and exceptions are caught, logged to Windows Event Log via `InfoLog.LogToEventViewer`, then re-thrown.
- `ParameterList` / `Parameter` — fluent parameter builder; `QuickAddInputParam` is the standard pattern for parameterised stored-procedure calls.

## 5. Authentication and Authorisation

### 5.1 Authentication

- **Mode:** Windows Authentication (`<authentication mode="Windows"/>` in `Web.config`)
- **IIS enforcement:** IIS negotiates NTLM/Kerberos with the browser before the ASP.NET pipeline runs
- **Identity resolution:** `VLAHeader.ascx::getUserDetails()` reads `HttpContext.Current.User.Identity.Name` (the Windows NT login), calls `clsUser.GetUserByNTLogin()` stored procedure, and stores user details in `Session`

### 5.2 Authorisation

Per-page `CheckPermissions()` method present on all non-home pages. Pattern:

```vb
' ReceiveBatch.aspx.vb example
Private Sub CheckPermissions()
    VLAHeader1.GetUserDetails()
    Dim sGroupName As String = Session(SessionVars.SV_HeaderGroupName)
    If sGroupName = "Customer" Then
        Response.Redirect("Home.aspx")
    ElseIf sGroupName = "Histopathology User" Then
        ' allowed
    ElseIf sGroupName = "Maintenance" Then
        ' allowed
    Else
        Response.Redirect("Home.aspx")
    End If
End Sub
```

**Three role groups (string literals):**
| Group Name | Access Level |
|---|---|
| `"Customer"` | Submission entry and viewing only |
| `"Histopathology User"` | Full lab workflow |
| `"Maintenance"` | Maintenance and administration functions |

No middleware-level or HTTP-module-level authorisation exists. No `[Authorize]` attributes. All role enforcement is inline per-page.

## 6. Session State

- **Mode:** `InProc` — `Web.config`: `<sessionState mode="InProc" ... timeout="90"/>`
- **Timeout:** 90 minutes
- **Key registry:** `SessionVars.vb` — all session keys defined as `Public Const String` values
- **Content:** DataTables, DataViews, DataSets, user identity fields, batch IDs, workflow navigation flags

Over 40 session keys defined in `SessionVars.vb`. Session is used as the primary state-passing mechanism between pages (substituting for URL parameters and hidden fields on complex multi-page workflows).

## 7. Runtime Assumptions

| Assumption | Detail |
|---|---|
| OS | Windows Server (IIS host) |
| Runtime | .NET Framework 4.0 |
| Compilation | `debug="true"` in `Web.config` — must be set `false` for production |
| IIS auth | Windows Authentication enabled; Anonymous Authentication disabled |
| Crystal runtime | SAP Crystal Reports 13.0.3500.0 installed in GAC on IIS host |
| SQL Server | `VM-APHADEV-003` — must be network-reachable from IIS host |
| Local disk | `C:\export\` must exist and be writable by the IIS application pool identity |
| Event Log | Application pool identity must have permission to write to Windows Application Event Log |
| Session | Single IIS instance; `InProc` session not cross-instance compatible |

## 9. Key Technical Constraints

| Constraint | Detail |
|---|---|
| No NuGet packages | All assemblies are direct GAC references (`packages.config` not present) |
| No ORM | All data access via ADO.NET stored procedures through `DataAccessLib` |
| No OWIN | No `Startup.cs` / middleware pipeline |
| No master page | Per-page header/footer control registration |
| InProc session | Single-instance assumption baked into architecture |
| Crystal Reports 13 | GAC-based; incompatible with .NET 5+ |
| Plaintext SQL credential | `Web.config` `DBConnectionString` contains username and password |
| Debug mode on | `compilation debug="true"` in `Web.config` |
| Local file writes | `ExcelExport.aspx` writes to `C:\export\` on the IIS host |
| Event Log dependency | `clsInfoLog` uses Windows Event Log; unavailable in sandboxed environments |
