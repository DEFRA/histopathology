# Histopathology System — Migration Plan

> **Status:** Proposed. Requires human approval before implementation begins.  
> **Source:** Generated by `modernise-to-modular-monolith.agent` (v1.1) on 2026-07-27.  
> **Target:** C# 14 / .NET 10 Modular Monolith — container-based deployment on Azure App Service.  
> **Data access decision:** Option A — Retain Stored Procedures via Dapper (user confirmed 2026-07-27).

---

## Guiding Principles

1. **No big-bang rewrite.** Each phase produces a independently deployable, testable increment.
2. **Behaviour preserved.** Business logic (batch status lifecycle, PG-number auto-reversal, histology ref types, role access rules) is translated verbatim — not redesigned.
3. **Database is frozen.** No stored procedure, table, column, or index changes during this migration. The database is the stable anchor.
4. **Rollback at every phase.** The legacy application remains deployable until Phase 6 cutover is validated.
5. **Human approval gate before each phase.** No phase begins without explicit sign-off.

---

## Phase Overview

```
Phase 0 — Foundation & Safety Net          [PREREQUISITE — MUST COMPLETE FIRST]
Phase 1 — Solution Scaffold + Infrastructure Module
Phase 2 — Authentication Migration
Phase 3 — Reporting Migration (Crystal Reports → PDF)
Phase 4 — Module-by-Module Domain + Repository Layer
Phase 5 — UI Migration (WebForms → Razor Pages)
Phase 6 — Infrastructure, CI/CD, and Cutover
```

Phases 2, 3, and 6-infra can begin in parallel after Phase 1 completes.  
Phase 5 cannot begin until Phase 4 is complete for the module being converted.

## Phase 2 — Authentication Migration

> **Status: Complete (2026-08-28).** Implemented as **Entra ID SAML 2.0** via `ITfoxtec.Identity.Saml2.MvcCore`
> (not the OIDC/`Microsoft.Identity.Web` approach originally proposed below — SAML 2.0 was the confirmed
> protocol per the Enterprise Application registration). `HistoPageModel` implements the two-gate model
> (SAML `ChallengeResult` for authentication, `tblUser`-backed group-claim check for authorisation) described
> in the exit criteria. The temporary `Login.cshtml` NTLogin bridge (ADR-006) has been decommissioned —
> see `docs/ADR/ADR-006-manual-login-page-bridge.md`. See `docs/Parity-Audit-Report.md` F-07 for the
> corresponding parity-audit closure.

**Purpose:** Replace Windows Authentication + `VLAHeader::getUserDetails()` with Azure Entra ID.

### Entry criteria
- Phase 1 exit criteria met
- Entra ID app registration created in Azure Portal (manual step — Azure admin required)
- Entra ID group IDs for `Customer`, `Histopathology User`, `Maintenance` confirmed

### Change set

1. Add `Microsoft.Identity.Web` NuGet to `Histo.Web`
2. Implement `AddMicrosoftIdentityWebAppAuthentication` in `Program.cs`
3. Define three `Authorization` policies mapped to Entra group claims
4. Add `Histo.Administration::UserService.GetUserByEntraUpnAsync()` — calls `GetUserByNTLogin` SP with the Entra UPN, caches result in `ISessionService`
5. Implement `ISessionService` with `UserContext` (UserID, Name, GroupName, AreaName)
6. Implement `_Layout.cshtml` with identity context (user name, group, area) read from `ISessionService`
7. Protect all Razor Pages with `[Authorize(Policy="...")]` as each page is converted (Phase 5)
8. Add auth smoke test: sign-in redirect round-trip, role claim present, session populated

### Stored procedures called in this phase

| SP Name | Purpose |
|---|---|
| `GetUserByNTLogin` | Map Entra UPN → application UserID, GroupCode, GroupName, AreaCode, AreaName |

### Exit criteria
- Sign-in redirect to Entra ID completes; user lands on home stub
- `ISessionService.CurrentUser` populated with correct UserID and GroupName
- Auth equivalence: same three role groups enforced; no access widening

> **Actual implementation note:** Sign-in is SP-initiated SAML 2.0 (`ChallengeResult("saml2")` →
> `/Saml2/login` → Entra ID → `POST /Saml2/Acs` → `AuthController`), not the OIDC redirect flow
> described above. Session population happens via `Session.PopulateFromClaims(User)` from the
> authenticated `ClaimsPrincipal` on first request after sign-in, rather than a dedicated
> `GetUserByEntraUpnAsync` call at ACS time. Functionally equivalent to the exit criteria — confirmed
> met.

### Rollback
Remove `Microsoft.Identity.Web` wiring from `Program.cs`. Legacy app continues running on Windows Auth.

## Phase 3 — Reporting Migration (Crystal Reports → PDF)

**Purpose:** Replace all 9 Crystal Reports with HTML/PDF rendering via `pdf-report-modernizer.agent`. Can run in parallel with Phase 2.

### Entry criteria
- Phase 0 reference PDFs committed
- `Histo.Infrastructure` available (Phase 1 done)

### Change set

Run `pdf-report-modernizer.agent` — the Civica-specific Crystal Reports moderniser (covers BSE, Histo, D2R2, PTLIMS). This is a self-contained, three-stage pipeline driven by `ReportDefinition.json`.

| Stage | What the agent does | Output |
|---|---|---|
| Stage 1 — Parse | Reads all 9 `.rpt` files; generates `ReportDefinition.json` with field mappings, sub-report links, and SP bindings | `docs/pdf-references/ReportDefinition.json` |
| Stage 2 — Template | Generates Razor HTML templates + CSS for each report; handles sub-report nesting for `HistologyReport` | `src/Histo.Reporting/Views/Reports/*.cshtml` |
| Stage 3 — Wire-up | Generates C# service/controller code; injects Dapper calls replacing XSD DataSet bindings; wires PDF rendering service | `src/Histo.Reporting/Services/`, `src/Histo.Reporting/Controllers/` |
| Validation | Runs RMSE pixel diff against Phase 0 reference PDFs | Pass/fail report per `.rpt` file |

> **Note on `HistologyReport` + `HistologySubReport`:** The sub-report nesting requires manual ViewModel design review before Stage 3 completes. The agent flags this as a manual review point; Sr Dev 1 reviews the generated ViewModel before committing.

All report code lives in `src/Histo.Reporting/`.

### Stored procedures called in this phase

All SPs called by the legacy Crystal Reports companion `.vb` classes — Dapper calls replace XSD DataSet binding.

### Exit criteria
- All 9 reports pass RMSE pixel diff validation against Phase 0 reference PDFs
- `GET /reports/{reportName}` returns a valid PDF in the test environment

### Rollback
Crystal Reports `.rpt` files and companion `.vb` classes remain in the legacy solution untouched. Revert `Histo.Reporting` project.

## Phase 4 — Domain and Repository Modules

**Purpose:** Convert each legacy `HistopathologyLib` domain class to a C# POCO + repository. One module at a time, starting with the least-coupled.

### Migration order (least-coupled first)

| Order | Module | Replaces | SPs Called |
|---|---|---|---|
| 4.1 | `Histo.Administration` | `clsUser`, `LookupData` | `GetUserByNTLogin`, `GetUsers`, `GetEditableLookups`, ~12 lookup SPs |
| 4.2 | `Histo.AuditLog` | `clsAuditLog` | `GetAuditLogBySubmission`, `GetAuditLogByDate`, `GetAuditLogByUser` |
| 4.3 | `Histo.QualityControl` | `clsQCNote` | QC note CRUD SPs |
| 4.4 | `Histo.Histology` | `clsBlock`, `clsHistology` | Block and histology ref SPs |
| 4.5 | `Histo.Submissions` | `clsBatch`, `clsBatchSubmission`, `clsBatchSummary`, `clsAnimal`, `clsTissue` | All batch/submission SPs (largest set) |

### Per-module change set pattern

For each module:

1. Define POCO record types mapping to SP result columns (replace DataTable columns)
2. Define `IXxxRepository` interface with one method per SP
3. Implement `XxxRepository : IXxxRepository` using Dapper
4. Define `XxxService` with business logic (extracted from ASPX code-behind and domain classes)
5. Register in `Program.cs` DI container
6. Write xUnit tests for service + repository integration tests against the real database

### Specific business logic to preserve

| Logic | Source | Target |
|---|---|---|
| PG-number auto-reversal | `clsAnimal.vb::NewRecord` | `Histo.Submissions::AnimalService.CreateAsync` |
| Batch status lifecycle constants | `clsBatch.vb` constants | `Histo.Submissions::BatchStatus` enum |
| DataSet table index access | `clsBatch.vb` integer constants | Eliminated — POCO properties by name |
| `HistologyRefType` enum | `Common.vb` | `Histo.Histology::HistologyRefType` enum |
| Block ref allocation order | `clsBlock.vb::GetOrder` | `Histo.Histology::BlockService.AllocateOrderAsync` |

### Exit criteria (per module)
- All repository integration tests pass against `Histology` database
- xUnit service tests pass with mocked repositories
- `dotnet build` zero errors

### Rollback (per module)
Module project can be reverted independently. Legacy `HistopathologyLib.dll` remains available.

## Phase 5 — UI Migration (WebForms → Razor Pages)

**Purpose:** Convert all 64 ASPX pages and 8 ASCX controls to Razor Pages in `Histo.Web`. This is the largest phase.

### Entry criteria
- Phase 4 module(s) complete for the pages being converted (pages depend on domain module)
- Phase 2 (auth) complete
- `_Layout.cshtml` complete

### Conversion order

| Batch | Pages | Module dependency | Complexity |
|---|---|---|---|
| 5.1 | ASCX controls → Partial Views / Layout | All modules | High (`VLAHeader` is critical path) |
| 5.2 | 18 simple display/menu pages | Administration, AuditLog | Low |
| 5.3 | 28 standard CRUD pages | Submissions, Histology, QC | Medium |
| 5.4 | 12 complex multi-step/copy workflows | Submissions, Histology | High |
| 5.5 | 6 report viewer pages | Reporting | High |
| 5.6 | Maintenance + admin pages | Administration | Medium |

### Per-page conversion rules

| Legacy pattern | Razor Pages equivalent |
|---|---|
| `Page_Load(IsPostBack=false)` | `OnGetAsync()` in PageModel |
| `Page_Load(IsPostBack=true)` | `OnPostAsync()` in PageModel |
| `Session[SessionVars.SV_*]` | `ISessionService` typed property |
| `Response.Redirect("X.aspx")` | `return RedirectToPage("X")` |
| `VLAHeader1.GetUserDetails()` | `ISessionService.CurrentUser` (populated by auth middleware) |
| `CheckPermissions()` | `[Authorize(Policy="...")]` attribute |
| DataGrid + DataView | `<table>` / `<partial>` with `IEnumerable<T>` model |
| UpdatePanel + ScriptManager | HTMX (`hx-post`, `hx-target`) for partial updates |
| `clsAppError.DisplayError` | `IAppLogger.LogError` + redirect to `Pages/Error.cshtml` |

### UpdatePanel strategy

All UpdatePanel usages are replaced with **HTMX**. This is the standard for the project. Pages that use UpdatePanel for partial postbacks are identified, and each postback is replaced with an HTMX `hx-post` call to a dedicated PageModel handler returning a Razor partial.

### Session state migration

`Session[SessionVars.SV_BatchDetails]` (DataSet) → `ISessionService.BatchWorkingState` (POCO, JSON-serialised to Redis).

All objects that were stored as DataTable/DataSet in session are converted to typed POCO classes. The Dapper repository returns POCOs directly; they are stored in Redis-backed session.

### Exit criteria (per batch)
- All converted pages render correctly in test environment
- `[Authorize]` policies enforce same access rules as legacy `CheckPermissions()`
- Automated E2E tests pass for converted pages

### Rollback (per batch)
Legacy ASPX pages remain deployable from the legacy solution. The new Razor Pages are in a separate project.

## Phase 6 — Infrastructure, CI/CD, and Cutover

**Purpose:** Provision Azure infrastructure, establish CI/CD pipeline, and perform the production cutover.

### Entry criteria
- All Phase 5 batches complete
- All E2E tests pass
- Auth equivalence validated

### Change set

1. **Azure infrastructure** — run `azure-infra-planner.agent` then `azure-infra-implementer.agent`:
   - App Service (Linux, .NET 10 container)
   - Azure SQL Database (existing `Histology` schema migrated or pointed to existing server)
   - Azure Cache for Redis
   - Key Vault (connection string, machineKey equivalent via Data Protection API)
   - Application Insights
   - Managed Identity SQL grant

2. **CI/CD pipeline** — run `devops-pipeline-modernizer.agent`:
   - GitHub Actions: build → test → publish → deploy to dev → UAT → prod
   - `dotnet publish` (not MSBuild)
   - Environment protection rules for UAT and prod approval gates

3. **Cutover:**
   - Deploy to App Service deployment slot (`staging`)
   - Run full E2E test suite against staging
   - Azure admin executes managed identity SQL grant
   - Traffic swap: `staging` → `production` slot
   - Monitor Application Insights for 30 minutes post-swap
   - Legacy IIS server kept live for 5 business days as rollback target

### Exit criteria
- Production smoke test passes (`GET /health` → 200)
- All three role groups can sign in and reach their respective pages
- At least one PDF report renders correctly in production
- No errors in Application Insights exception telemetry after 30 minutes

### Rollback
Swap deployment slot back to legacy App Service. Legacy IIS remains available for 5 days.

## Risk Register

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Stored procedure result set changes between environments | Low | High | Compare SP output against Phase 0 reference data before any deployment |
| Entra ID group IDs not matching legacy role groups | Medium | High | Auth equivalence test suite in Phase 2 validates role mapping before Phase 5 |
| Session POCOs not JSON-serialisable | Medium | Medium | All POCO classes validated in Phase 4 tests before session integration |
| PDF pixel diff failures on `HistologyReport` sub-report | High | Medium | Manual ViewModel design for sub-report; acceptance threshold 5% RMSE |
| `GetUserByNTLogin` SP expects Windows NT login format; Entra UPN differs | High | High | Phase 2 task: map Entra UPN → existing NT login in user table (one-time data migration or SP parameter update in agreement with DB team) |
| UpdatePanel replacement incomplete for complex pages | Medium | Medium | HTMX standardisation; each UpdatePanel usage inventoried in Phase 5.3 before implementation |
| Redis session connection failure | Low | High | Fallback to in-memory session in dev; Redis health check in CI smoke test |
