## 1. Architecture Summary

The target architecture is a **Modular Monolith** deployed as a **single container**, composed of well-defined modules with enforced internal boundaries. It is deployed to **Azure App Service (Linux container)** backed by **Azure SQL Database**, with secrets in **Azure Key Vault** and telemetry via **Application Insights**.

The system is **not** broken into microservices. Each module is a separate C# project within the `.slnx` solution, with explicit dependency rules enforced by project references. All modules share a single SQL database and a single process at runtime.

## 2. Module Boundaries

### 2.1 Module definitions

| Module | Project | Replaces | Owns |
|---|---|---|---|
| `Histo.Web` | ASP.NET Core Razor Pages | `HistopathologySystem` (64 ASPX + 8 ASCX) | HTTP surface, auth, session, layout, routing |
| `Histo.Submissions` | Class library | `HistopathologyLib/clsBatch`, `clsBatchSubmission`, `clsBatchSummary`, `clsAnimal`, `clsTissue` | Submission/batch/sample/tissue domain and repositories |
| `Histo.Histology` | Class library | `HistopathologyLib/clsBlock`, `clsHistology`, `clsHistologyRef` | Block, histology reference domain and repositories |
| `Histo.QualityControl` | Class library | `HistopathologyLib/clsQCNote` | QC notes domain and repositories |
| `Histo.Reporting` | Class library | 9 Crystal Reports + companion `.vb` classes | PDF report rendering via Playwright |
| `Histo.AuditLog` | Class library | `HistopathologyLib/clsAuditLog` | Audit log queries |
| `Histo.Administration` | Class library | `HistopathologyLib/clsUser`, `LookupData` | User management, pick-lists |
| `Histo.Infrastructure` | Class library | `DataAccessLib` entirely | DB connection factory, logging, configuration |
| `Histo.Tests` | xUnit test project | _(no tests today)_ | Unit + integration tests |

### 2.2 Dependency rules

```
Histo.Web
  → Histo.Submissions
  → Histo.Histology
  → Histo.QualityControl
  → Histo.Reporting
  → Histo.AuditLog
  → Histo.Administration
  → Histo.Infrastructure

All domain modules (Submissions, Histology, QC, Reporting, AuditLog, Administration)
  → Histo.Infrastructure only

Histo.Infrastructure
  → no internal dependencies

No module may reference Histo.Web.
No cross-module references between domain modules (e.g. Submissions must not reference QualityControl).
Cross-cutting domain queries (e.g. audit log of a submission) are orchestrated in Histo.Web service layer,
not by one module calling into another.
```

## 4. Data Access Strategy — Option A: Retain Stored Procedures via Dapper

**Decision recorded:** Stored procedures already exist in the `Histology` database and contain the data access logic. The application layer calls them. This pattern is retained in the modernised system.

**Rationale:** The stored procedures are the database's API contract. They exist, are tested by production use, and changing them is a database-level risk outside the scope of this migration. Retaining them eliminates all database schema risk during the application rewrite.

### Implementation pattern

Replace the legacy `DataAccess`/`TBCultureDA` chain with **Dapper** (`Dapper` NuGet, v2.x):

```csharp
// Histo.Infrastructure/IDbConnectionFactory.cs
public interface IDbConnectionFactory
{
    SqlConnection CreateConnection();
}

// Histo.Infrastructure/SqlConnectionFactory.cs
public class SqlConnectionFactory : IDbConnectionFactory
{
    private readonly string _connectionString;
    public SqlConnectionFactory(string connectionString) => _connectionString = connectionString;
    public SqlConnection CreateConnection() => new SqlConnection(_connectionString);
}
```

Repository implementation pattern (one per module):

```csharp
// Histo.Submissions/Repositories/BatchRepository.cs
public class BatchRepository : IBatchRepository
{
    private readonly IDbConnectionFactory _db;
    public BatchRepository(IDbConnectionFactory db) => _db = db;

    public async Task<Batch?> GetByIdAsync(int batchId)
    {
        using var conn = _db.CreateConnection();
        return await conn.QueryFirstOrDefaultAsync<Batch>(
            "GetCommonBatchDetails",
            new { ID = batchId },
            commandType: CommandType.StoredProcedure);
    }

    public async Task<IEnumerable<BatchSubmission>> GetSubmissionsAsync(int batchId)
    {
        using var conn = _db.CreateConnection();
        return await conn.QueryAsync<BatchSubmission>(
            "GetBatchSubmissions",
            new { BatchID = batchId },
            commandType: CommandType.StoredProcedure);
    }
}
```

**POCO models** replace DataSet/DataTable. Each stored procedure result set maps to a typed POCO. Example:

```csharp
// Histo.Submissions/Models/Batch.cs
public record Batch(
    int Id,
    string Status,
    DateTime? ReceivedDate,
    int ReceivedById,
    string HistologyRef,
    // ... all columns returned by GetCommonBatchDetails
);
```

### Stored procedure source control

All stored procedures must be extracted from the `Histology` database and committed to source control as `.sql` files under `database/stored-procedures/`. This is a **Phase 1 prerequisite** (see Migration Plan). No stored procedure modification is in scope for this migration.

### Connection string migration

Legacy: SQL auth username/password in `Web.config` (plaintext).  
Target: Managed Identity — `Authentication=Active Directory Default` — see [ADR-005](ADR/ADR-005-data-access-dapper-stored-procedures.md) and the infrastructure instructions.

## 5. Authentication and Authorisation

### 5.1 Authentication

Replace Windows Authentication + `VLAHeader::getUserDetails()` with **Azure Entra ID** via `Microsoft.Identity.Web`:

```csharp
// Program.cs
builder.Services.AddMicrosoftIdentityWebAppAuthentication(builder.Configuration, "AzureAd");
builder.Services.AddAuthorization(options =>
{
    options.AddPolicy("HistopathologyUser", policy =>
        policy.RequireClaim("groups", builder.Configuration["AzureAd:HistopathologyUserGroupId"]));
    options.AddPolicy("Customer", policy =>
        policy.RequireClaim("groups", builder.Configuration["AzureAd:CustomerGroupId"]));
    options.AddPolicy("Maintenance", policy =>
        policy.RequireClaim("groups", builder.Configuration["AzureAd:MaintenanceGroupId"]));
});
```

### 5.2 Authorisation

Replace 60+ `CheckPermissions()` per-page methods with Razor Pages `[Authorize(Policy="...")]` attributes:

```csharp
[Authorize(Policy = "HistopathologyUser")]
public class ReceiveBatchModel : PageModel { ... }

[Authorize(Policy = "Customer")]
public class AddSubmissionModel : PageModel { ... }
```

### 5.3 Identity resolution

Replace `VLAHeader.ascx::getUserDetails()` → `clsUser.GetUserByNTLogin()` with:
- Claims read from Entra ID token via `IHttpContextAccessor`
- On first login, `clsUser.GetUserByNTLogin` equivalent maps Entra UPN → application `UserID` via `GetUserByNTLogin` stored procedure (called once per session, result cached in `ISessionService`)

## 6. Session State

### 6.1 Typed session service

Replace the untyped `Session[SessionVars.SV_*]` string bag with a strongly-typed DI service:

```csharp
// Histo.Web/Services/ISessionService.cs
public interface ISessionService
{
    UserContext? CurrentUser { get; set; }
    int? ActiveBatchId { get; set; }
    BatchWorkingState? BatchWorkingState { get; set; }
    // ... typed properties for each workflow state object
}
```

### 6.2 Session provider

Initial deployment: **ASP.NET Core distributed session** backed by **Azure Cache for Redis** (`Microsoft.Extensions.Caching.StackExchangeRedis`). All objects stored in session must be JSON-serialisable.

POCO models (replacing DataTable/DataSet) are JSON-serialisable by design.

## 7. Reporting

Crystal Reports 13 is replaced by **Playwright headless PDF rendering** (see `pdf-migration-orchestrator` agent):

- `Histo.Reporting` project contains `IPlaywrightPdfService`, `_PdfLayout.cshtml`, and one Razor view per report
- Reports are rendered server-side to PDF bytes and streamed to the browser
- No runtime dependency on SAP Crystal Reports DLLs

## 11. What Is NOT Changing

| Item | Rationale |
|---|---|
| All stored procedures in `Histology` database | Retained as-is. Application layer calls them by name. No stored procedure is modified or deleted during this migration. |
| Database schema | No table, column, or index changes. |
| Business logic | All business rules (PG-number auto-reversal, batch status lifecycle, block ref allocation, histology ref types) are preserved verbatim in the C# equivalent. |
| Three role groups | `Customer`, `Histopathology User`, `Maintenance` role names are mapped 1:1 to Entra ID group policies. |
